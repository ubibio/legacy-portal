[개요]
화면이 로그인 대상과 결재자 선택지로 쓰는 사용자 목록을 제공하고, 빈 DB 에는 기본 사용자를 만든다.

[상세 기능 요구사항]
1) GET /api/users 로 전체 사용자(id · name · email · role · dept)를 반환한다.
2) 직급(role): 1=사원, 2=팀장, 3=임원. 팀장 이상이 결재 · 공지 게시 권한을 가진다.
3) 애플리케이션 시작 시 사용자가 0명이면 김사원(1) · 박팀장(2) · 이임원(3) · 최사원(1) 4명을 만든다.

[입력 / 출력]
- 입력: 없음
- 출력: 사용자 목록 JSON, 시작 로그 '>> 초기 사용자 4명 생성 완료'

[제약 조건 / 비기능 요구사항]
- 이미 사용자가 있으면 초기 데이터를 다시 넣지 않는다.
- 응답 필드 형식을 바꾸지 않는다(화면이 role 숫자로 직급명을 만든다).

[검증 기준]
- 빈 DB 로 시작하면 /api/users 가 4명을 반환한다.
- 재시작해도 MariaDB 사용 시 사용자 수가 늘지 않는다.

10. 검토 의견 · 후속 과제

구분내용
보존 대상GET /api/users URL·메서드, JSON 필드 5개(id·name·email·role·dept)와 role 숫자 표현, 초기 4명의 이름·이메일·role·부서·생성 순서, 시작 로그 문자열, "0명일 때만 삽입" 가드, DB role 정수 1/2/3, 권한 판정 role >= 2.
개선 대상(1) 엔티티 직접 노출 → UserResponse record DTO 분리(필드 동일). (2) 필드명 userRepo 약어 → userRepository(UserController·DataSeeder, 네이밍 규칙). (3) 매직넘버 1/2/3 → UserRole enum + AttributeConverter(R07). (4) System.out.println → 로거. (5) ddl-auto=create-drop 때문에 MariaDB 에서도 재시작마다 데이터가 지워진다 - "재시작해도 늘지 않는다"는 가드가 아니라 스키마 재생성 덕분에 성립. 운영 데이터 보존이 필요하면 update/validate + 마이그레이션 검토(REQ-DA-002 · REQ-SE-001 과 함께).
연계 요구사항REQ-F-003/004(결재 권한), REQ-F-010(공지 게시 권한), REQ-IF-001(메일 수신 주소), REQ-DA-002(DB 선택)
