# 01. 구조 파악 - 사내 업무 포털(legacy-portal)

> **이 문서는 무엇을·왜 보는가**
> 리팩토링의 첫 단계는 코드를 고치는 것이 아니라 **"지금 무엇이 어디서 무슨 일을 하는지"를 지도로 그리는 것**이다.
> 구조와 책임 분배를 먼저 파악해야 어디에 냄새(스멜)가 몰려 있는지, 무엇을 특성화 테스트로 먼저 고정해야 하는지, 어디부터 손대야 안전한지 판단할 수 있다.
> 이 문서는 그 판단의 출발점이 되는 **현재(레거시) 상태의 사실 기록**이며, 옳고 그름의 평가는 이후 진단 문서에서 다룬다.

- 기준 시점: 커밋 `4ee9553` (main)
- 규모: 프로덕션 Java 18개 파일 · 약 780줄 / **테스트 0개**

---

## 1. 기술 스택 · 실행 환경

| 항목 | 내용 |
|------|------|
| 언어 / 프레임워크 | Java 21 · Spring Boot 3.2 · Spring Data JPA |
| DB | MariaDB(`localhost:3306/portal`) 접속 가능하면 사용, 아니면 **H2 인메모리 자동 전환** (`DataSourceConfig`) |
| 화면 | `src/main/resources/static/index.html` 한 장 (Tailwind + 순수 JS, `fetch`로 REST 호출) |
| 실행 / 테스트 | `.\mvnw.cmd spring-boot:run` (8080) / `.\mvnw.cmd test` |
| 외부 연동 | 메일·감사로그 모두 **실제 발송/기록 없이 콘솔 출력**(실습용) |

## 2. 패키지 구조

```
kr.hull.portal
├── PortalApplication      스프링 부트 진입점
├── DataSourceConfig       MariaDB ↔ H2 자동 선택
├── DataSeeder             기동 시 사용자 4명 초기 데이터
├── approval/  (결재)  Approval · ApprovalRepository · ApprovalService · ApprovalController
├── notice/    (공지)  Notice   · NoticeRepository   · NoticeService      (컨트롤러 없음)
├── schedule/  (일정)  Schedule · ScheduleRepository · ScheduleService    (컨트롤러 없음)
├── user/      (사용자) User    · UserRepository     · UserController
└── common/    (공통)  SmtpMailSender(메일) · FileAuditLogger(감사로그)
```

도메인(업무)별 폴더 안에 Entity + Repository + Service (+ Controller)가 모여 있는 **패키지-바이-피처** 구조다.

## 3. 계층 · 의존 관계

```
index.html ──HTTP──▶ Controller ──▶ Service ──▶ Repository(JPA) ──▶ DB(MariaDB/H2)
                                      │
                                      ├─ new SmtpMailSender()   ← 주입이 아닌 직접 생성
                                      └─ new FileAuditLogger()  ← 주입이 아닌 직접 생성
```

- Repository만 생성자 주입이고, 메일·로그 협력 객체는 서비스가 **직접 `new`** 한다.
- 모든 서비스가 `UserRepository`를 함께 사용한다(권한 판정·메일 수신자 조회).
- 컨트롤러는 **Entity를 그대로 JSON으로 반환**하고, 요청은 `Map<String, Object>`로 받는다(DTO 없음).

## 4. 서비스별 책임

### 4-1. `ApprovalService` (결재) - 197줄, 이 프로젝트의 핵심

| public 메서드 | 하는 일 |
|---|---|
| `create(title, content, type, priority, drafterId, approverId, amount, urgent)` | 결재 문서를 **임시저장(0)** 상태로 생성. `urgent`면 우선순위 3(높음). 감사로그 기록 |
| `processApproval(id, userId, action, reason)` | `action` 코드로 상신/승인/반려/취소를 한 메서드에서 분기 처리 (아래 표) |
| `statusLabel(approval)` | 상태 숫자 → 화면용 한글 라벨 |
| `amountGrade(approval)` | 금액 → 등급 S/A/B/C (1000만/100만/10만 기준) |
| `myDrafts(userId)` / `myInbox(userId)` | 내가 기안한 목록 / 내가 결재자인 목록 |

`processApproval` 상태 전이 규칙:

| action | 허용 조건 | 결과 | 부수효과 |
|---|---|---|---|
| 1 상신 | 상태 0(임시저장) | → 1(상신). **지출(type 1) & 100만원 이상이면 우선순위 3으로 상향** | 결재자에게 `[결재요청]` 메일, 감사로그 |
| 2 승인 | 상태 1 + 요청자 = 결재자 + role ≥ 2 | → 2(승인) | 기안자에게 `[결재승인]` 메일, 감사로그 |
| 3 반려 | 상태 1 + 요청자 = 결재자 + role ≥ 2 | → 3(반려), 사유 저장 | 기안자에게 `[결재반려]` 메일, 감사로그 |
| 9 취소 | 상태 0 또는 1 + 요청자 = 기안자 | → 9(취소) | 감사로그 (메일 없음) |

- 조건을 만족하지 않거나, 문서·사용자가 없으면 **예외 없이 조용히 무시**(return)한다. → 특성화 테스트로 고정해야 할 레거시 동작.
- 검증·영속화·메일 본문 생성·감사로그·권한 판정·화면 라벨까지 한 클래스가 모두 맡는다(**God Class**).

### 4-2. `NoticeService` (공지) - 83줄

| public 메서드 | 하는 일 |
|---|---|
| `create(title, content, category, writerId, pinned)` | 공지를 **임시(0)** 상태로 생성, 감사로그 |
| `publish(id, userId)` | role ≥ 2이고 상태 0일 때 → **게시(1)**. **긴급(category 2)이면 전 직원에게 메일**. 감사로그 |
| `statusLabel(notice)` | 0 임시 · 1 게시 · 9 내림 → 라벨 |

- 권한 없음·이미 게시됨 등은 역시 **조용히 무시**.
- 감사로그·메일 본문·권한 판정(`role >= 2`)이 `ApprovalService`와 **복붙 수준으로 중복**.
- REST 컨트롤러가 없어 화면/API에서는 아직 쓰이지 않는다.

### 4-3. `ScheduleService` (일정) - 81줄

| public 메서드 | 하는 일 |
|---|---|
| `create(title, ownerId, startAt, endAt, location)` | 입력 검증(제목·시간 누락, 종료<시작) + **같은 사람의 시간 겹침 검사**(취소(9) 일정 제외) 후 **예정(0)** 으로 저장, 감사로그 |
| `confirm(id, userId)` | 본인 일정이고 상태 0이면 → **확정(1)**, 감사로그 |

- 검증 실패·겹침이면 **`null` 반환**(원인 구분 불가), `confirm`은 조건 불만족 시 조용히 무시.
- 메일은 쓰지 않고 감사로그만 사용. 컨트롤러 없음.

### 4-4. `user` (사용자)

- 별도 서비스 없이 `UserController`가 `UserRepository`를 직접 호출 → `GET /api/users` (로그인 화면의 사용자 선택용).
- `role`: 1 사원 · 2 팀장 · 3 임원. 다른 서비스의 권한 판정(`role >= 2`) 기준.
- 초기 데이터(`DataSeeder`): 1 김사원 · 2 박팀장 · 3 이임원 · 4 최사원.

### 4-5. `common` (공통)

| 클래스 | 책임 | 사용처 |
|---|---|---|
| `SmtpMailSender.send(to, subject, body)` | 메일 발송(실제로는 콘솔 출력) | Approval, Notice |
| `FileAuditLogger.write(line)` | 감사로그 기록(실제로는 콘솔 `[AUDIT]` 출력) | Approval, Notice, Schedule |

인터페이스 없는 구체 클래스라, 사용하는 서비스가 직접 생성한다 → 테스트에서 가짜로 바꿔 끼울 수 없다.

## 5. 외부 계약(API) - 리팩토링 시 변경 금지 대상

| 메서드 · URL | 요청 | 응답 | 연결 서비스 |
|---|---|---|---|
| `GET /api/users` | - | `User[]` | (Repository 직접) |
| `POST /api/approvals` | `{title, content, type, priority, drafterId, approverId, amount?, urgent?}` | `Approval` | `create` |
| `POST /api/approvals/{id}/process` | `{userId, action, reason?}` | 본문 없음(200) | `processApproval` |
| `GET /api/approvals/drafts/{userId}` | - | `Approval[]` | `myDrafts` |
| `GET /api/approvals/inbox/{userId}` | - | `Approval[]` | `myInbox` |

## 6. 코드값(매직넘버) 정리 - DB에 정수 그대로 저장됨

| 대상 | 값 |
|---|---|
| 결재 상태 `Approval.status` | 0 임시저장 · 1 상신 · 2 승인 · 3 반려 · 9 취소 |
| 결재 처리 `action` | 1 상신 · 2 승인 · 3 반려 · 9 취소 |
| 결재 유형 `Approval.type` | 1 지출 · 2 휴가 · 3 구매 · 4 기타 |
| 우선순위 `Approval.priority` | 1 낮음 · 2 보통 · 3 높음 |
| 공지 상태 `Notice.status` | 0 임시 · 1 게시 · 9 내림 |
| 공지 분류 `Notice.category` | 1 일반 · 2 긴급 · 3 인사 |
| 일정 상태 `Schedule.status` | 0 예정 · 1 확정 · 9 취소 |
| 사용자 역할 `User.role` | 1 사원 · 2 팀장 · 3 임원 |

## 7. 구조 파악에서 드러난 사실 요약

**보존 대상** (리팩토링 중 바꾸지 않음)
- 위 5장의 API 엔드포인트·요청/응답 형식, 서비스 public 메서드 시그니처
- 6장의 DB 저장 정수값
- 조건 불만족 시 **조용히 무시** / **`null` 반환**하는 동작, 상신 시 우선순위 자동 상향 규칙

**개선 대상** (다음 진단 문서에서 상세화)
- `ApprovalService` 쏠림(God Class)과 `processApproval` 긴 메서드·중첩 if
- 정수 코드값 → 도메인 이름을 가진 enum (`@Convert`로 DB값 유지)
- 메일·감사로그 직접 `new` → 생성자 주입
- 감사로그·메일 본문·권한 판정의 서비스 간 중복
- 상태 규칙이 서비스에 있는 빈약한 도메인 모델 → 엔티티로 이동
- Entity 직접 노출 / `Map` 요청 → DTO(record) 분리
- **테스트 0개** → 리팩토링 전에 특성화 테스트부터 작성 필요
