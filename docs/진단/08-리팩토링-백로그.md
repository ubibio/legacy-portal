# 08. 리팩토링 백로그 - 우선순위순 작업 목록

> **이 문서는 무엇을·왜 보는가**
> 진단(01~07)은 "무엇이 문제인가"를 말할 뿐, 그대로는 일이 되지 않는다. 백로그(Backlog)는 스멜을 **한 번에 끝낼 수 있는 작업 단위로 쪼개고, 의존 관계와 심각도에 따라 줄 세운 할 일 목록**이다.
> 리팩토링은 작은 단계를 하나씩 끝내고 매번 테스트로 동작이 그대로인지 확인해야 안전하므로, 이 문서는 각 작업의 **선행 조건 · 보존할 것 · 완료 기준**을 함께 적어 "지금 무엇을, 어디까지 하면 되는가"를 정하는 기준으로 삼는다.

- 기준 시점: 커밋 `7117ff4` (main)
- 근거: [07-심각도점수](07-심각도점수.md)(영향도 × 난이도) · [06-심각도-표](06-심각도-표.md)(작업 단계) · [smells.md](../smells.md)(스멜 ID)

## 우선순위를 정한 규칙

1. **안전망 먼저** - 테스트(S01)가 없으면 어떤 작업도 "동작 보존"을 증명할 수 없으므로 무조건 1번
2. **Quick Win 다음** - 영향 높음 · 쉬움(S06·S05·S07·S08·S10). 위험이 작고, 이후 작업을 쉽게 만든다
3. **핵심 과제는 의존 순서대로** - 심각도는 S02 > S03 > S04·S09 순이지만, S02·S03은 다른 스멜이 풀려야 고칠 수 있으므로 **S04 → S03 → S09 → S02** 로 진행
4. **가벼운 스멜(★)은 따로 잡지 않고** 관련 작업에 곁들인다
5. **동작이 바뀌는 것(S19)·설정 문제(S20)는 백로그에서 제외** - 리팩토링이 끝난 뒤 재설계 단계

크기: **S** 반나절 이하 · **M** 하루 안팎 · **L** 이틀 이상

## 작업 상세

### R01. 특성화 테스트 작성 - 1순위 · L

- **왜 먼저**: 이후 모든 작업의 "동작이 그대로다"를 증명하는 유일한 수단. 지금 테스트는 0개
- **할 일**
  - 결재 `processApproval`: 상신 · 승인 · 반려 · 취소 각각 **정상 전이 + 조용히 무시되는 경우**(상태 불일치, 결재자 아님, 권한 없음, 기안자 아님, 없는 문서·사용자, 정의되지 않은 action)
  - 결재 `create`: 초기 상태 0, `urgent` 면 우선순위 3 / 상신 시 지출 100만원 이상 우선순위 3
  - 공지 `publish`: 권한 없음 무시, 이미 게시 무시, 긴급(2)이면 전 직원 메일
  - 일정 `create`: 입력 오류 · 시간 겹침이면 `null`, 취소(9) 일정은 겹침에서 제외 / `confirm`: 본인 · 예정일 때만
  - `statusLabel` · `amountGrade` 경계값(10만 · 100만 · 1000만)
  - 메일 · 감사로그 **출력 문자열** (현재 콘솔 출력 - 스프링 부트 `OutputCaptureExtension` 등으로 고정)
  - API 5개의 요청 · 응답 JSON 형식 (`MockMvc`)
- **완료 기준**: 전부 green. 기대값은 **정수 리터럴(0/1/2/3/9)** 로 작성. 테스트 이름만 한글 시나리오명, 변수는 영어

### R02. 감사로그 기록기 주입 + 로그 조립 공통화 - 2순위 · S

- **해결**: S06(직접 `new` 3곳), S05(로그 조립 6곳)
- **할 일**: `FileAuditLogger` 에서 인터페이스 추출 → 구현체를 `@Component` 로 등록 → 3개 서비스 생성자 주입. 시각 포맷 + 줄 조립을 한 메서드로 모은다
- **보존**: 출력 `[AUDIT] [시각] 동작 id=.. by=..` 그대로, **`APPROVAL CREATE ... type=` 꼬리 유지**
- **완료 기준**: 서비스 안 `new FileAuditLogger()` 0곳, `DateTimeFormatter.ofPattern` 1곳, R01 green

### R03. 메일 발송기 주입 + 메일 본문 조립 공통화 - 3순위 · S

- **해결**: S06(직접 `new` 2곳), S07(메일 본문 4곳)
- **할 일**: `SmtpMailSender` 인터페이스 추출 · 빈 등록 · 2개 서비스 생성자 주입. `안녕하세요 {이름}님,` 본문과 `[말머리] 제목` 조립을 한 곳으로
- **보존**: 제목 · 본문 문자열(줄바꿈 위치, `기안자ID:` · `사유:` 추가 줄), 수신자, 발송 조건
- **완료 기준**: 서비스 안 `new SmtpMailSender()` 0곳, R01 green

### R04. 권한 판정을 `User` 메서드로 - 4순위 · S

- **해결**: S08(`role >= 2` 3곳)
- **할 일**: `User` 에 `hasApprovalAuthority()` 같은 의미 있는 메서드를 두고 3곳에서 호출 (R07에서 `UserRole` enum으로 내부만 교체)
- **보존**: 팀장(2) 이상 기준, 권한 없으면 조용히 무시
- **완료 기준**: 서비스에 `getRole() >= 2` 0곳, R01 green

### R05. 공지 게시 · 일정 생성 중첩 풀기 - 5순위 · S

- **해결**: S10(`publish` 중첩 4, `Schedule.create` 중첩 3), S11(`flag1`, `n`, `sc`, `u` 등), S15(조회-무시 패턴)
- **할 일**: 조건 불만족 시 조기 반환, 겹침 검사를 `hasOverlappingSchedule(...)` 로 추출, 긴급 메일 발송부 추출, 약어 이름을 의미 있는 이름으로
- **보존**: 무시 · `null` 반환 동작, 취소 일정 제외 규칙, `ScheduleService` 의 null 체크 없는 소유자 비교
- **완료 기준**: 두 메서드 중첩 2 이하, R01 green

### R06. 결재 상태 · 처리 구분 enum 도입 - 6순위 · M

- **해결**: S04 중 가장 큰 덩어리(결재 상태 16곳 + 처리 구분 4곳), S14(결재 라벨), S18(미사용 값 누락 방지)
- **할 일**: `ApprovalStatus`(0·1·2·3·9 + 라벨), `ApprovalAction`(1·2·3·9) 도입, `AttributeConverter` + `@Convert` 로 DB에 정수 저장, `statusLabel` 은 enum 라벨 위임
- **보존**: DB 정수값, API로 주고받는 정수, 모르는 action 무시, 모르는 상태 라벨 `알수없음`. **`@Enumerated` 금지**
- **완료 기준**: `ApprovalService` 에 상태 · action 숫자 0곳, DB 저장값 동일, R01 green (테스트는 정수 그대로)

### R07. 나머지 코드값 enum + 금액 기준 상수 - 7순위 · M

- **해결**: S04 나머지, S14(공지 라벨), S18
- **할 일**: `UserRole` · `NoticeStatus` · `NoticeCategory` · `ScheduleStatus` · `ApprovalType` · `ApprovalPriority` enum + Converter. 금액 기준은 이름 있는 상수로 - **우선순위 상향 기준과 등급 A 기준(둘 다 100만원)은 따로**
- **보존**: R06과 같음. 공지 내림(9) · 일정 취소(9) 등 **안 쓰이는 값도 enum에 포함**
- **완료 기준**: 서비스에 코드값 숫자 0곳, R01 green

### R08. `processApproval` 분해 - 8순위 · M (심각도 ★★★★★)

- **해결**: S03(86줄 · 중첩 5 · 복잡도 약 25), S11(`d` · `u` · `s` · `proc` · `tmp`)
- **선행 이유**: 주입(R02 · R03) · 권한 메서드(R04) · enum(R06)이 끝나야 분기 안이 짧아져 안전하게 쪼갤 수 있다
- **할 일**: `submit` / `approve` / `reject` / `cancel` private 메서드로 추출, 각 메서드는 조기 반환, 본체는 action에 따라 위임만
- **보존**: **`processApproval(id, userId, action, reason)` 시그니처**, 분기마다 조건 순서와 무시 동작, 지출 100만원 이상 우선순위 상향
- **완료 기준**: 본체 20줄 이하, 추출 메서드 각 20줄 · 중첩 2 이하, R01 green

### R09. 상태 전이 · 판정 규칙을 엔티티로 (Rich Domain) - 9순위 · M (★★★★)

- **해결**: S09(빈약한 도메인 · 기능 욕심), S08 마무리
- **할 일**: `Approval` 에 `submit()` · `approve()` 등 전이 메서드와 `isApprover(userId)` · `isDrafter(userId)` 질의, `updatedAt` 갱신을 엔티티 안으로. 금액 등급 계산도 `Approval` 로. 같은 방식으로 `Notice` · `Schedule`
- **보존**: 전이 조건 · 결과, `amountGrade` 경계값, public 메서드 시그니처
- **완료 기준**: 서비스가 `setStatus(...)` 를 직접 부르는 곳 0곳, R01 green

### R10. `ApprovalService` 책임 분리 - 10순위 · M (심각도 1위 ★★★★★)

- **해결**: S02(거대 클래스)
- **선행 이유**: R02~R09로 책임 대부분이 이미 바깥으로 빠져, 이 단계에선 남은 덩어리만 정리하면 된다
- **할 일**: 결재 알림(메일 대상 · 문구 결정)을 별도 협력 객체로, 화면용 표시(`statusLabel` · `amountGrade`)는 enum · 엔티티 위임으로 정리. 서비스는 **조회 → 도메인 호출 → 저장 → 알림**의 조율만
- **보존**: 서비스의 public 메서드 이름 · 시그니처 전부(내부 위임만)
- **완료 기준**: `ApprovalService` 100줄 이하 · 책임 "조율" 하나, R01 green

### R11. 요청 / 응답 DTO(record) 분리 - 11순위 · M

- **해결**: S12(Entity 직접 노출, `Map` 요청)
- **할 일**: 결재 생성 · 처리 요청 record, 결재 · 사용자 응답 record 도입, 컨트롤러는 Entity 대신 record를 주고받음
- **보존**: **JSON 필드 이름 · 형식 · 숫자 타입을 레거시와 1:1**, URL · HTTP 메서드
- **완료 기준**: 컨트롤러에 `Map<String, Object>` 0곳 · Entity 반환 0곳, R01의 API 테스트 green

### R12. 긴 파라미터 목록 정리 - 12순위 · S

- **해결**: S13(`ApprovalService.create` 8개)
- **할 일**: R11의 요청 record를 받는 내부 메서드를 두고, 기존 8개 파라미터 `create` 는 그 메서드로 위임
- **보존**: 기존 `create(title, content, type, priority, drafterId, approverId, amount, urgent)` 시그니처
- **완료 기준**: R01 green

### R13. 시계 주입 · 변명 주석 정리 - 13순위 · S

- **해결**: S17(`LocalDateTime.now()` 13곳), S16(주석 스멜)
- **할 일**: 필요하면 `Clock` 빈 주입, 이름 · enum으로 의미가 드러난 곳의 변명 주석 삭제. 대신 CLAUDE.md 규칙의 `[리팩토링]` 헤더 · 인라인 주석은 남긴다
- **완료 기준**: R01 green

## 백로그 밖 - 재설계 단계로 넘기는 것

| 스멜 | 이유 |
|---|---|
| S19 조용한 실패 · `null` 반환 (★★★★) | 고치면 예외 · 실패 응답이 생겨 **겉보기 동작이 바뀐다.** 리팩토링이 아니므로 R01~R13이 끝난 뒤 따로 다룬다 |
| S20 DB 접속 정보 하드코딩 (★) | 코드 구조가 아니라 설정 외부화 문제 |

## 모든 작업 공통 규칙

- 작업 하나 = 커밋 하나. 시작 전 · 끝난 뒤 **R01 특성화 테스트 green** 확인
- **테스트 본문(호출 · 기대값)은 고치지 않는다.** 패키지 이동에 따른 import 줄만 예외 - 바꿨으면 diff로 확인받는다
- 바꾼 코드에는 `[리팩토링] 레거시 X → Y (기법 · 이유)` 주석을 남기고, 보존 대상과 개선 대상을 구분해 적는다
