# 05. 강결합 진단 - 직접 `new` 로 만드는 의존성

> **이 문서는 무엇을·왜 보는가**
> 클래스가 협력 객체를 `new SmtpMailSender()` 처럼 **스스로 만들면**, 그 구체 클래스에 단단히 묶인다(강결합, Tight Coupling). 구현을 바꾸려면 쓰는 쪽 코드를 모두 고쳐야 하고, 테스트에서 진짜 메일 대신 가짜(Fake·Mock)를 끼울 수도 없다. 이는 "구체가 아닌 추상에 의존하라"는 의존성 역전 원칙(DIP) 위반이다.
> 이 문서는 직접 생성되는 의존성을 모두 찾아 **고쳐야 할 결합과 괜찮은 `new` 를 구분**하고, 인터페이스 도입 + 생성자 주입(DI)으로 바꿀 대상과 순서를 정하는 근거로 삼는다.

- 기준 시점: 커밋 `7d68470` (main)
- 조사 대상: `src/main/java` 전체의 `new 클래스(...)` 와, `new` 는 아니지만 같은 효과를 내는 정적 호출(`LocalDateTime.now()` 등)
- 이전 문서: [01](01-구조-파악.md) · [02](02-중복-코드.md) · [03](03-긴-메서드.md) · [04](04-매직넘버.md)

## 판단 기준 - 모든 `new` 가 나쁜 건 아니다

| 구분 | 설명 | 예 |
|---|---|---|
| 🔴 **고쳐야 할 결합** | **행위(부수효과)를 가진 협력 객체**를 직접 생성. 바꿔 끼우거나 테스트에서 대체해야 할 대상 | 메일 발송기, 로그 기록기 |
| 🟡 **숨은 결합** | `new` 는 없지만 정적 호출로 외부 자원(시계·콘솔·DB 드라이버)에 직접 묶임 | `LocalDateTime.now()`, `System.out` |
| 🟢 **문제 없음** | 데이터를 담는 객체(엔티티·값 객체)를 만드는 것. 갈아끼울 이유가 없음 | `new Approval()`, `new User(...)` |

|:-:|---|---|:-:|
| 1 | `new SmtpMailSender()` | `approval/ApprovalService.java:37` | 🔴 |
| 2 | `new FileAuditLogger()` | `approval/ApprovalService.java:38` | 🔴 |

**고쳐야 할 결합은 5곳, 대상 클래스는 2개**(`SmtpMailSender`, `FileAuditLogger`)다.

## 2. 의존 관계 그림 (현재)

```
                 생성자 주입 ✅                       직접 new ❌
ApprovalService ──────────▶ ApprovalRepository     ──▶ SmtpMailSender   (구체 클래스)
                ──────────▶ UserRepository         ──▶ FileAuditLogger  (구체 클래스)

NoticeService   ──────────▶ NoticeRepository       ──▶ SmtpMailSender
                ──────────▶ UserRepository         ──▶ FileAuditLogger

ScheduleService ──────────▶ ScheduleRepository     ──▶ FileAuditLogger
                ──────────▶ UserRepository
```

- 같은 서비스 안에서 **Repository는 생성자 주입, 메일·로그는 직접 `new`** 로 방식이 섞여 있다.
- 서비스마다 각자 인스턴스를 만들어, 스프링이 관리하는 빈이 아닌 **보이지 않는 객체 5개**가 생긴다.
- `common` 의 두 클래스에는 인터페이스가 없다 → 쓰는 쪽이 **구체 클래스 이름을 import** 한다(`ApprovalService.java:3-4`, `NoticeService.java:3-4`, `ScheduleService.java:3`).

## 3. 🔴 고쳐야 할 결합 상세

### 3-1. `SmtpMailSender` - 메일 발송기 (2개 서비스, 4곳에서 호출)

| 생성 위치 | 호출 위치 | 무엇을 보내나 |
|---|---|---|
| `ApprovalService.java:37` | `:106` · `:123` · `:143` | 결재 요청 · 승인 · 반려 알림 |
| `NoticeService.java:24` | `:66` | 긴급 공지 전 직원 알림 |

**결합 때문에 생기는 문제**
- **테스트 불가**: 결재 승인 테스트를 돌리면 메일 발송 코드가 그대로 실행된다. 가짜 발송기로 바꿔 "누구에게·무슨 제목으로 보냈는지" 검증할 방법이 없다. (지금은 콘솔 출력이라 티가 안 나지만, 실제 SMTP였다면 테스트마다 메일이 나간다.)
- **교체 비용**: 실제 메일 서버(JavaMailSender)나 사내 메신저로 바꾸려면 두 서비스를 모두 열어 고쳐야 한다.
- **설정 불가**: 생성자 인자 없는 `new` 라 SMTP 주소·계정 같은 설정을 넣을 통로가 없다.

### 3-2. `FileAuditLogger` - 감사로그 기록기 (3개 서비스, 6곳에서 호출)

| 생성 위치 | 호출 위치 |
|---|---|
| `ApprovalService.java:38` | `:65`(create) · `:165`(writeAudit - 상신·승인·반려·취소) |
| `NoticeService.java:25` | `:45`(create) · `:70`(publish) |
| `ScheduleService.java:20` | `:63`(create) · `:77`(confirm) |

**결합 때문에 생기는 문제**
- **이름과 실제가 다르다**: 이름은 *File* 로거지만 실제는 콘솔(`System.out`) 출력이다(`common/FileAuditLogger.java:11`). 출력 대상(파일·DB·콘솔)을 바꾸려면 이 클래스 자체를 고치거나 세 서비스를 모두 고쳐야 한다.
- **테스트 불가**: "승인하면 감사로그가 `APPROVAL APPROVE id=.. by=..` 로 남는다"를 검증하려면 표준출력을 가로채는 꼼수 외엔 방법이 없다.
- **중복과 결합이 겹침**: 로그 줄 조립 코드가 6곳에 복사돼 있어([02](02-중복-코드.md) D1), 주입으로 바꿀 때 공통 메서드 추출을 함께 하는 게 효과적이다.

## 4. 🟡 숨은 결합 - `new` 는 없지만 바꿔 끼울 수 없는 것

| 대상 | 위치 | 문제 | 우선순위 |
|---|---|---|:-:|
| `LocalDateTime.now()` (시스템 시계) | `ApprovalService.java:57, 58, 62, 98, 116, 136, 154, 164` · `NoticeService.java:40, 44, 69` · `ScheduleService.java:62, 76` (**13곳**) | 생성·수정 시각과 로그 시각이 실행할 때마다 달라 **테스트에서 기대값을 고정할 수 없다** | 중간 |
| `System.out.println` (콘솔) | `common/SmtpMailSender.java:12-16` · `common/FileAuditLogger.java:11` · `DataSeeder.java:28` · `DataSourceConfig.java:30, 39` | 출력 대상이 콘솔로 고정. 단, common 두 클래스는 **실습용 가짜 구현**이라 인터페이스 뒤로 숨기면 해결됨 | 낮음 |
| `DriverManager.getConnection(...)` | `DataSourceConfig.java:51-53` | 시작 시 DB 연결 확인용 설정 코드. 인프라 설정 영역이라 **리팩토링 대상 아님** | - |

- 시각은 스프링의 `Clock` 빈을 주입받아 `LocalDateTime.now(clock)` 으로 바꾸면 테스트에서 고정 시계를 쓸 수 있다. 다만 시각을 검증하는 특성화 테스트가 필요해질 때 도입해도 늦지 않다.
- 참고(범위 밖): `DataSourceConfig.java:23-25` 에 DB 접속 계정·비밀번호가 상수로 박혀 있다. 결합이라기보다 설정 외부화 문제라 재설계 단계에서 다룬다.

## 5. 🟢 문제 없는 `new` - 바꾸지 않는다

| 대상 | 위치 | 이유 |
|---|---|---|
| `new Approval()` · `new Notice()` · `new Schedule()` | 각 서비스 `create` | **새 데이터(엔티티)를 만드는 행위 자체가 업무**다. 갈아끼울 구현이 없다. (다만 setter를 줄줄이 부르는 방식은 [03](03-긴-메서드.md)·Rich Domain 개선에서 정적 팩토리/생성자로 정리 가능) |
| `new User(...)` ×4 | `DataSeeder.java:24-27` | 데모 초기 데이터 |
| `DataSourceBuilder.create()` | `DataSourceConfig.java:31, 40` | 스프링 `@Bean` 메서드 안에서 빈을 만드는 정상적인 설정 코드 |

## 6. 정리 - 보존 대상 vs 개선 대상

**보존 대상** (주입 방식으로 바꿔도 그대로여야 하는 것)
- 메일: **언제·누구에게·어떤 제목/본문으로** 보내는지 (콘솔 출력 형식 `=== MAIL ===` / `TO:` / `SUBJECT:` 포함)
- 감사로그: 출력 문자열 `[AUDIT] [시각] 동작 id=.. by=..` 과 기록 시점
- 서비스 **public 생성자 외 메서드 시그니처** - 생성자에 인자가 늘어나는 것은 스프링이 주입하므로 외부 계약 변경이 아니다

**개선 대상** (권장 순서)

| 순서 | 대상 | 기법 | 결과 |
|:-:|---|---|---|
| 1 | `FileAuditLogger` | 인터페이스 추출(예: `AuditLogWriter`) → 현재 클래스를 구현체로 `@Component` 등록 → 3개 서비스 **생성자 주입** | 직접 `new` 3곳 제거, 테스트에서 기록 내용 검증 가능 |
| 2 | `SmtpMailSender` | 인터페이스 추출(예: `MailSender` 성격의 이름) → `@Component` 등록 → 2개 서비스 생성자 주입 | 직접 `new` 2곳 제거, 테스트에서 가짜 발송기 사용 |
| 3 | 감사로그·메일 본문 조립 | 주입과 함께 공통 메서드로 추출 ([02](02-중복-코드.md) D1·D2) | 중복 10곳 → 각 1곳 |
| 4 | `LocalDateTime.now()` | 필요 시 `Clock` 주입 | 시각 관련 테스트 고정 |

**바꾼 뒤 모습 (목표)**

```
ApprovalService ──▶ ApprovalRepository, UserRepository
                ──▶ «interface» MailSender      ◀── SmtpMailSender (@Component)
                ──▶ «interface» AuditLogWriter  ◀── FileAuditLogger (@Component)
```

> 순서 1·2는 **동작(출력 문자열·발송 시점)을 전혀 바꾸지 않는** 구조 변경이라 가장 안전한 첫 리팩토링이다. 동시에 이후 모든 특성화 테스트에서 메일·로그를 검증할 수 있게 해 주는 **테스트 가능성의 전제 조건**이기도 하다.
