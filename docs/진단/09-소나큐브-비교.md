# 09. SonarQube 정적 분석 vs 수동 진단 비교

> **이 문서는 무엇을·왜 보는가**
> 정적 분석 도구(SonarQube)는 정해진 **규칙(Rule)에 맞는 코드 모양**을 빠르고 빠짐없이 찾지만, "이 숫자가 업무 규칙이다", "이 클래스가 책임을 너무 많이 진다" 같은 **의미와 설계**는 판단하지 못한다. 사람의 진단은 그 반대다.
> 이 문서는 SonarQube 결과를 우리 진단(01~08, 스멜 S01~S20)과 하나씩 맞대어 **도구가 잡은 것 · 놓친 것 · 사람이 놓친 것**을 가르고, 리팩토링 중 도구를 무엇에 믿고 쓸지 정하는 근거로 삼는다.

- 분석 대상: 커밋 `0cec80e` (main), `src/main/java` 653줄
- 도구: SonarQube Community Build 26.6.0.123539 · 기본 품질 프로필 **Sonar way** · Java 21 · `mvnw clean verify sonar:sonar`
- 결과 화면: http://localhost:9000/dashboard?id=kr.hull.portal%3Alegacy-portal

## 3. 분석

### 3-1. 둘 다 찾은 것 - 도구가 사람을 확인해 줌

- **`processApproval` (S03)**: 우리는 86줄 · 중첩 5 · **순환 복잡도 약 25**로 쟀고, SonarQube는 **인지 복잡도 52**로 쟀다. 두 숫자는 다른 척도다.
  - 순환 복잡도: 실행 경로 수 → **테스트 케이스가 몇 개 필요한가**
  - 인지 복잡도: 중첩될수록 가중치를 더 줌 → **사람이 읽기 얼마나 어려운가**
  - 순환 25에 비해 인지 52가 두 배인 것은 이 메서드의 문제가 분기 수보다 **중첩 깊이**에 있다는 뜻이다. 백로그 R08의 "조기 반환으로 중첩 5 → 2"가 정확한 처방임을 뒷받침한다.
- **시계 `now()` (S17)**: 우리가 05에서 센 13곳과 S8688 13건이 줄 번호까지 같다. 단순 패턴은 도구가 사람만큼 정확하다.
- **파라미터 8개 (S13)**: S107 그대로 일치.
- **중첩 if (S03 · S10)**: S1066 9건은 우리가 03에서 계단으로 그린 지점과 같다. 다만 SonarQube의 처방은 "`&&` 로 합쳐라"인데, 이는 **중첩 깊이만 줄일 뿐 분기의 의미는 그대로**다. 우리 처방(분기별 메서드 추출 + 조기 반환)이 더 근본적이다.

### 3-2. SonarQube만 잘 본 것 / 다르게 본 것

- **콘솔 직접 출력 (S106, 9건)**: 우리는 `SmtpMailSender` · `FileAuditLogger` 의 콘솔 출력을 "실습용 가짜 구현이라 인터페이스 뒤로 숨기면 된다"며 낮게 봤다. SonarQube는 로거 대신 `System.out` 을 쓴 것 자체를 MAJOR로 본다. **R02 · R03 에서 인터페이스 뒤로 숨기더라도 구현체 안의 S106은 남는다**는 점을 알려 준다.
- **비밀번호 하드코딩 (S20)**: 우리는 "설정 외부화 문제, 범위 밖 ★"로 뒀고 SonarQube는 **BLOCKER**로 보안 등급을 E로 떨어뜨렸다.
  - 차이의 이유: SonarQube는 맥락을 모르고 "코드에 비밀번호 = 유출 위험"으로 일반 판정한다. 우리는 "로컬 데모 DB · 리팩토링 대상 아님"이라는 맥락을 알았다.
  - 그래도 이 저장소는 **공개 GitHub**에 올라가 있다. 맥락을 고려해도 무시할 문제는 아니므로 재설계 단계 우선순위를 올릴 근거가 된다.
- **if-else → switch (S6880)**: 우리는 `statusLabel` 을 "두 서비스에 같은 모양이 있다(중복)"로 봤고, SonarQube는 "형태가 낡았다"로 봤다. 우리 처방(R06: 라벨을 enum이 갖게 함)을 따르면 if-else 사슬 자체가 사라져 두 지적이 함께 해소된다.

### 3-3. SonarQube가 놓친 것 - 사람의 진단이 필요한 영역

| 놓친 것 | 왜 못 잡나 |
|---|---|
| **매직넘버 (S04, 45곳)** | 매직넘버 규칙(S109)이 기본 프로필 Sonar way에 **들어 있지 않다.** 켜더라도 -1 · 0 · 1은 예외라, 이 프로젝트의 핵심 코드값 0 · 1(임시저장 · 상신 등)은 여전히 못 잡는다 |
| **감사로그 중복 (S05, 6곳)** | 복사본마다 동작 문자열 · 변수 이름이 조금씩 달라 "같은 토큰 10줄 이상" 기준에 안 걸린다. 대신 잡은 중복 2블록은 `Approval` · `Notice` 의 **getter/setter 6줄**(id · title · content)로, 오히려 고칠 필요가 없는 것이다 |
| **직접 `new` (S06)** | `new` 자체는 문법상 정상. "협력 객체를 주입받아야 한다"는 설계 판단은 규칙으로 표현되지 않는다 |
| **빈약한 도메인 · 거대 클래스 (S09 · S02)** | 클래스 크기 규칙은 있지만 197줄은 기준 미만. "책임이 7가지"라는 판단은 의미를 알아야 한다 |
| **권한 판정 중복 (S08)** | `role >= 2` 세 줄은 짧아 중복 기준에 못 미치고, "같은 업무 규칙"이라는 사실은 모른다 |
| **나쁜 이름 (S11)** | 이름 규칙(S117 등)은 **형식**(camelCase)만 본다. `d` · `u` 는 형식상 올바르다 |
| **DTO 부재 · 조용한 실패 (S12 · S19)** | `Map` 형변환 · `return;` 은 문법상 정상. API 계약 · 실패 전달 방식은 설계 문제 |

공통점: **업무 의미를 알아야 보이는 문제**는 도구가 못 잡는다. 그리고 그것들이 우리 심각도 상위에 몰려 있다 - ★★★★ 이상 6개 중 S04 · S09 · S19 는 전혀 못 잡았고, S02 는 이슈가 한 파일에 몰린 것으로 간접적으로만 드러났다.

### 3-4. 등급을 그대로 믿으면 안 되는 이유

- **유지보수성 A** 는 "부채 비율 1.5%"(고칠 시간 ÷ 코드를 새로 짤 시간)로 매긴다. 규칙 위반 개수 × 규칙별 수정 시간의 합이라, **규칙에 안 걸리는 설계 문제는 0분**으로 계산된다. 우리가 ★★★★★로 본 `ApprovalService` 가 있어도 A가 나온다.
- **품질 게이트 OK** 는 기본 게이트가 **새로 바뀐 코드**에만 조건을 걸기 때문이다. 첫 분석이라 새 코드가 없어 통과했을 뿐, 레거시 전체가 괜찮다는 뜻이 아니다.
- **커버리지 0.0%** 가 실제로 가장 정직한 신호다. 품질 게이트가 이를 막지 않았다는 점이 S01을 1순위로 둔 이유를 다시 확인해 준다.

## 5. 정리

- SonarQube는 **"모양"을 빠르고 정확하게** 잡는다 - 시계 13곳 · 파라미터 8개 · 중첩 if 9곳은 사람과 같은 답을 냈다.
- 그러나 **"의미"는 못 본다** - 매직넘버 · 강결합 · 감사로그 중복 · 빈약한 도메인 · 나쁜 이름 등 우리 진단의 핵심 11개를 하나도 잡지 못했고, 유지보수성 A · 품질 게이트 OK 라는 겉보기 좋은 결과를 냈다.
- 그래서 역할을 나눈다
  - **설계 판단(무엇을 고칠까)** → 사람의 진단 (01~08)
  - **진척 측정(얼마나 고쳤나) · 회귀 감시(새로 망가뜨렸나)** → SonarQube. 백로그 작업 하나가 끝날 때마다 다시 분석해 이슈 수 · 인지 복잡도 · 커버리지 변화를 기록한다
- 기준선(리팩토링 전): **이슈 40 · 인지 복잡도 최대 52 · 커버리지 0% · 중복 1.3% · 보안 E**
