# 02. 중복 코드 진단 - Approval · Notice · Schedule 서비스

> **이 문서는 무엇을·왜 보는가**
> 중복 코드(Duplicated Code)는 같은 지식이 여러 곳에 흩어져 있다는 신호다. 규칙 하나를 바꿀 때 복사본을 전부 찾아 똑같이 고쳐야 하고, 하나라도 빠뜨리면 곳마다 동작이 어긋난다(DRY 원칙 위반).
> 이 문서는 세 서비스에 반복되는 코드를 **어디에·몇 번·어떤 모양으로** 있는지 찾아 모아, 공통 모듈 추출(메서드 추출·클래스 추출) 리팩토링의 대상과 순서를 정하는 근거로 삼는다.
> 동시에 복사본끼리 **미묘하게 다른 부분**을 기록해, 하나로 합칠 때 겉보기 동작(로그 문자열·메일 문구)이 바뀌지 않도록 한다.

- 기준 시점: 커밋 `4ee9553` (main)
- 대상: [`ApprovalService`](../../src/main/java/kr/hull/portal/approval/ApprovalService.java) · [`NoticeService`](../../src/main/java/kr/hull/portal/notice/NoticeService.java) · [`ScheduleService`](../../src/main/java/kr/hull/portal/schedule/ScheduleService.java)
- 이전 문서: [01-구조-파악](01-구조-파악.md)

## D1. 감사로그 시각 포맷 + 기록 - 6곳 (가장 많이 복붙됨)

```java
String now = LocalDateTime.now().format(DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss"));
audit.write("[" + now + "] <동작> id=" + <id> + " by=" + <사용자id>);
```

| 위치 | 동작 문자열 | 비고 |
|---|---|---|
| `ApprovalService.java:62-65` (`create`) | `APPROVAL CREATE` | ⚠ 끝에 ` type=<유형>` 이 **추가로** 붙는다 |
| `ApprovalService.java:163-166` (`writeAudit`) | `APPROVAL SUBMIT/APPROVE/REJECT/CANCEL` | 유일하게 메서드로 추출된 곳 - 그러나 `create`는 이걸 안 쓴다 |
| `NoticeService.java:44-45` (`create`) | `NOTICE CREATE` | |
| `NoticeService.java:69-70` (`publish`) | `NOTICE PUBLISH` | |
| `ScheduleService.java:62-63` (`create`) | `SCHEDULE CREATE` | |
| `ScheduleService.java:76-77` (`confirm`) | `SCHEDULE CONFIRM` | |

- **같은 지식**: 시각 형식 `yyyy-MM-dd HH:mm:ss`, 줄 모양 `[시각] 동작 id=.. by=..`.
- **문제**: 로그 형식을 바꾸려면 6곳을 고쳐야 한다. `ApprovalService`는 `writeAudit`로 반쯤 추출했다가 `create`에 복사본이 남은 **불완전한 중복 제거** 상태다.
- **합칠 때 보존할 차이**: `APPROVAL CREATE` 줄의 ` type=` 꼬리. 공통 메서드로 합치더라도 출력 문자열은 지금과 똑같아야 한다.
- **개선 방향**: 공통 감사로그 컴포넌트(예: `AuditLogWriter.write(action, targetId, actorId)`)로 추출하고 생성자 주입 - D6과 함께 처리.

## D2. 메일 본문 조립 + 발송 - 4곳

```java
String body = "안녕하세요 " + <수신자>.getName() + "님,\n" + "<안내문>\n제목: " + <제목> [+ 추가줄];
mail.send(<수신자>.getEmail(), "[<말머리>] " + <제목>, body);
```

| 위치 | 수신자 | 제목 말머리 | 안내문 | 추가줄 |
|---|---|---|---|---|
| `ApprovalService.java:101-106` (상신) | 결재자 | `[결재요청]` | 결재 요청이 도착했습니다. | `\n기안자ID: ..` |
| `ApprovalService.java:119-123` (승인) | 기안자 | `[결재승인]` | 결재가 승인되었습니다. | - |
| `ApprovalService.java:138-143` (반려) | 기안자 | `[결재반려]` | 결재가 반려되었습니다. | `\n사유: ..` |
| `NoticeService.java:62-66` (긴급공지) | 전 직원(루프) | `[긴급공지]` | 긴급 공지가 게시되었습니다. | - |

- **같은 지식**: 인사말 `안녕하세요 {이름}님,` 형식, 제목 `[{말머리}] {제목}` 형식, 받는 주소 = `user.getEmail()`.
- 결재 3곳은 수신자 조회(`userRepo.findById(..).orElse(null)`) → null이면 건너뜀 패턴까지 함께 복사됨.
- **합칠 때 보존할 차이**: 줄바꿈 위치(`님,\n` 다음 `안내문\n제목:`)와 추가줄 유무가 곳마다 다르다 - 결과 문자열이 1글자도 바뀌면 안 된다.
- **개선 방향**: 메일 본문 조립을 한 곳(예: 알림 메일 작성 메서드/클래스)으로 모으고, 말머리·안내문·추가줄만 인자로 넘긴다.

## D3. 권한 판정 `role >= 2` (팀장 이상) - 3곳

| 위치 | 용도 |
|---|---|
| `ApprovalService.java:114` | 승인 권한 |
| `ApprovalService.java:133` | 반려 권한 (바로 위 승인 분기와 동일 코드) |
| `NoticeService.java:56` | 공지 게시 권한 |

- **같은 지식**: "팀장(2) 이상이면 결재·게시할 수 있다"는 권한 규칙이 매직넘버 `2`로 세 번 적혀 있다.
- **문제**: 권한 기준이 바뀌면(예: 임원만) 세 곳을 모두 찾아야 하고, 숫자 `2`는 검색으로도 찾기 어렵다.
- **개선 방향**: `User`에 의미 있는 메서드(예: `hasApprovalAuthority()`)로 옮기고(Rich Domain), 역할은 enum + `@Convert`로 DB값(1/2/3) 유지.

## D4. 조회 후 null이면 조용히 return - 3곳

```java
X x = repo.findById(id).orElse(null);           if (x == null) return;
User u = userRepo.findById(userId).orElse(null); if (u == null) return;
```

| 위치 | 대상 |
|---|---|
| `ApprovalService.java:76-84` (`processApproval`) | 결재 문서 + 사용자 |
| `NoticeService.java:50-53` (`publish`) | 공지 + 사용자 |
| `ScheduleService.java:68-71` (`confirm`) | 일정 + 사용자 |

- `ScheduleService.confirm`은 조회한 `u`를 **이후에 쓰지도 않는다** - 복사해 오면서 따라온 흔적(사용자가 없으면 무시되는 동작 자체는 보존 대상).
- **보존 대상**: 없으면 예외 없이 무시하는 동작. 합치더라도 예외로 바꾸지 않는다.
- **개선 방향**: `Optional` 기반 조기 반환으로 의도를 드러내는 정도까지만 정리.

## D5. 상태 숫자 → 라벨 변환 `statusLabel` - 2곳

| 위치 | 매핑 |
|---|---|
| `ApprovalService.java:169-179` | 0 임시저장 · 1 상신 · 2 승인 · 3 반려 · 9 취소 · 그 외 `알수없음` |
| `NoticeService.java:76-82` | 0 임시 · 1 게시 · 9 내림 · 그 외 `알수없음` |

- 값은 다르지만 **구조(if-else 사다리 + `알수없음` 기본값)가 판박이**다. "숫자 코드 ↔ 이름" 표가 서비스 안에 하드코딩되어 있다.
- **개선 방향**: 상태별 enum(`ApprovalStatus`, `NoticeStatus`)에 라벨을 넣어 enum이 자기 이름을 알게 한다. 정의되지 않은 값의 `알수없음` 반환은 보존.

## D6. 협력 객체 직접 `new` - 5곳

| 위치 | 코드 |
|---|---|
| `ApprovalService.java:37-38` | `new SmtpMailSender()` · `new FileAuditLogger()` |
| `NoticeService.java:24-25` | `new SmtpMailSender()` · `new FileAuditLogger()` |
| `ScheduleService.java:20` | `new FileAuditLogger()` |

- 서비스마다 같은 협력 객체를 **각자 따로 생성**한다. 구현을 바꾸거나 테스트에서 가짜로 교체하려면 모든 서비스를 고쳐야 한다.
- **개선 방향**: 인터페이스 도입 + 스프링 빈 등록 + 생성자 주입(DIP). D1·D2를 공통 모듈로 추출할 때 함께 처리하면 효과가 크다.

## D7. 상태 변경 + `updatedAt` 갱신 + 저장 - 4곳 (Approval 내부)

```java
d.setStatus(<새 상태>);
d.setUpdatedAt(LocalDateTime.now());
repo.save(d);
```

- `ApprovalService.java:97-99`(상신) · `115-117`(승인) · `134-137`(반려, 사유 저장 포함) · `153-155`(취소)
- **개선 방향**: `Approval`에 상태 전이 메서드(예: `submit()`, `approve()`)를 두고 시각 갱신을 엔티티 안으로 이동(Rich Domain). 상태 전이 조건·결과는 보존.

## D8. "본인인지" 판정 - 4곳

| 위치 | 비교 |
|---|---|
| `ApprovalService.java:113`, `132` | `d.getApproverId() != null && d.getApproverId().equals(userId)` (결재자 본인, 같은 식 2번) |
| `ApprovalService.java:152` | `d.getDrafterId() != null && d.getDrafterId().equals(userId)` (기안자 본인) |
| `ScheduleService.java:72` | `sc.getOwnerId().equals(userId)` (소유자 본인) |

- 같은 의도("이 사용자가 당사자인가")를 매번 null 체크 + `equals`로 풀어 쓴다.
- ⚠ `ScheduleService`만 **null 체크가 없다** - 패턴이 같아 보여도 합치면 동작이 달라질 수 있는 지점(현재는 `ownerId`가 null이면 NPE). 리팩토링 단계에선 그대로 둔다.
- **개선 방향**: 엔티티에 `isApprover(userId)`, `isDrafter(userId)`, `isOwner(userId)` 같은 질의 메서드로 이동.

## 정리 - 보존 대상 vs 개선 대상

**보존 대상** (중복을 합쳐도 바뀌면 안 되는 것)
- 감사로그 출력 문자열 - 특히 `APPROVAL CREATE ... type=` 꼬리
- 메일 제목·본문 문자열(줄바꿈 위치, 추가줄 유무 포함)과 수신자
- 권한 기준(`role >= 2`), 대상이 없거나 조건이 안 맞을 때 조용히 무시하는 동작
- `statusLabel`의 `알수없음` 기본값, `ScheduleService`의 null 체크 없는 소유자 비교

**개선 대상** (권장 순서)
1. **D6 → D1**: 감사로그를 공통 컴포넌트로 추출하고 생성자 주입 (6곳 → 1곳, 가장 효과 큼)
2. **D6 → D2**: 메일 본문 조립을 공통화하고 메일 발송기 주입 (4곳 → 1곳)
3. **D3 · D8**: 권한·당사자 판정을 `User`·각 엔티티 메서드로 이동
4. **D5 · D7**: 상태 enum(라벨 포함, `@Convert`로 DB값 유지)과 엔티티 상태 전이 메서드 도입
5. **D4**: 조회-무시 패턴 정리 (동작 보존 범위 안에서)

> 어느 단계든 **먼저 특성화 테스트로 현재 출력(로그·메일·상태값)을 고정**한 뒤에 합친다. 테스트가 0개인 지금은 중복을 합치는 순간의 동작 변화를 감지할 수단이 없다.
