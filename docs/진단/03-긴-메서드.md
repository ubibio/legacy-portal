# 03. 긴 메서드 · 깊은 중첩 진단

> **이 문서는 무엇을·왜 보는가**
> 긴 메서드(Long Method)와 깊은 중첩(Deep Nesting)은 한 메서드가 여러 책임을 떠안았다는 가장 눈에 띄는 신호다. 길수록 한 화면에 안 들어오고, 중첩이 깊을수록 "지금 어떤 조건들이 겹친 상태인지"를 머릿속에 쌓아 둬야 해서 읽기·테스트·수정이 모두 어려워진다.
> 이 문서는 모든 메서드의 **줄 수와 중첩 깊이를 측정**해, 메서드 추출·조기 반환(Guard Clause)·도메인 이동 리팩토링을 **어디부터 할지 우선순위**를 정하는 근거로 삼는다.

- 기준 시점: 커밋 `95be4be` (main)
- 측정 대상: `src/main/java` 전체 메서드(생성자 포함). 1줄짜리 getter/setter는 표에서 생략
- 이전 문서: [01-구조-파악](01-구조-파악.md) · [02-중복-코드](02-중복-코드.md)

## 측정 기준

| 항목 | 기준 |
|---|---|
| **줄 수** | 메서드 선언 줄부터 닫는 `}` 까지(빈 줄·주석 포함) |
| **중첩 깊이** | 메서드 본문 안에서 `if` / `else` / `for` / `while` 블록이 겹친 최대 단계. 본문 바로 아래 = 0, `if` 하나 안 = 1 |
| **경고 기준** | 줄 수 **50줄 초과** = 긴 메서드, 중첩 **3단계 이상** = 깊은 중첩 (일반적 클린코드 권장값: 메서드 20줄 이하·중첩 2단계 이하) |

## 1. 50줄 초과 메서드

| 메서드 | 위치 | 줄 수 | 최대 중첩 | 판정 |
|---|---|:-:|:-:|---|
| `ApprovalService.processApproval(id, userId, action, reason)` | `approval/ApprovalService.java:75-160` | **86** | **5** | 🔴 긴 메서드 + 깊은 중첩 |

**50줄을 넘는 메서드는 `processApproval` 하나뿐**이지만, 기준의 1.7배 길이에 중첩 5단계로 프로젝트 전체에서 압도적이다.

### 1-1. `processApproval` 해부

action 값에 따라 4개 업무가 한 메서드 안에 `if-else if` 사다리로 이어져 있다.

| 구간 | 줄 범위 | 줄 수 | 최대 중첩 | 하는 일 |
|---|---|:-:|:-:|---|
| 공통 준비 | 75-89 | 15 | 1 | 문서·사용자 조회(없으면 조용히 return), `s`·`proc` 지역변수 |
| `proc == 1` 상신 | 90-109 | 20 | 3 | 상태 검사 → 지출 100만원↑ 우선순위 상향 → 저장 → 결재자 메일 → 감사로그 |
| `proc == 2` 승인 | 110-128 | 19 | **5** | 상태 → 결재자 본인 → 권한 → 저장 → 기안자 메일 → 감사로그 |
| `proc == 3` 반려 | 129-148 | 20 | **5** | 승인과 같은 구조 + 반려 사유 저장 |
| `proc == 9` 취소 | 149-160 | 12 | 3 | 상태(0 또는 1) → 기안자 본인 → 저장 → 감사로그 |

가장 깊은 지점(승인 분기)의 조건 겹침:

```
if (proc == 2)                                   ← 1  처리 구분
  if (s == 1)                                    ← 2  상태가 상신인가
    if (approverId != null && approverId.equals) ← 3  요청자가 결재자 본인인가
      if (u.getRole() >= 2)                      ← 4  팀장 이상인가
        if (drafter != null)                     ← 5  메일 받을 기안자가 있는가
          mail.send(...)
```

- 메일 한 통을 보내는 코드를 읽으려면 **조건 5개를 동시에 기억**해야 한다.
- 분기 조건 수로 센 순환 복잡도(Cyclomatic Complexity)는 **약 25** - 일반 권장값(10 이하)의 2.5배. 모든 경로를 테스트로 덮으려면 최소 25개 안팎의 경우가 필요하다.
- 한 메서드가 **상태 전이 규칙 + 권한 판정 + 영속화 + 메일 조립 + 감사로그**를 모두 한다(단일 책임 원칙 위반).

## 3. 깊은 중첩(3단계 이상) 상세

### `NoticeService.publish` - 25줄, 중첩 4

```
if (u.getRole() >= 2)          ← 1  팀장 이상인가
  if (n.getStatus() == 0)      ← 2  임시 상태인가
    if (n.getCategory() == 2)  ← 3  긴급 공지인가
      for (User member : ...)  ← 4  전 직원 루프
        mail.send(...)
```

- 길이는 짧지만 권한 → 상태 → 분류 → 루프가 계단식으로 쌓였다.
- 권한·상태 검사를 **조기 반환(Guard Clause)** 으로 바꾸면 2단계까지 낮아진다(조용히 무시하는 동작은 그대로).

### `ScheduleService.create` - 39줄, 중첩 3

```
for (Schedule s : repo.findByOwnerId(ownerId))       ← 1  기존 일정 루프
  if (s.getStatus() != 9)                            ← 2  취소 일정 제외
    if (s.getStartAt().isBefore(endAt) && ...)       ← 3  시간 겹침
      flag1 = true;
```

- 입력 검증(3개) + 겹침 검사 + 생성·저장 + 감사로그가 한 메서드에 있다(39줄, 기준 근접).
- 겹침 검사 루프를 `hasOverlappingSchedule(...)` 같은 메서드로 추출하면 `flag1` 이라는 의미 없는 이름도 함께 사라진다.

## 4. 정리 - 보존 대상 vs 개선 대상

**보존 대상** (메서드를 쪼개도 바뀌면 안 되는 것)
- `processApproval(id, userId, action, reason)` 의 **public 시그니처와 action 코드(1/2/3/9)** - 내부에서 상신·승인·반려·취소 메서드로 **위임만** 한다
- 각 분기의 조건 순서와 결과: 조건 불만족·대상 없음 → **조용히 무시**, 상신 시 지출 100만원↑ 우선순위 상향
- `ScheduleService.create` 의 `null` 반환, 취소(9) 일정을 겹침 검사에서 제외하는 규칙
- 메일·감사로그의 발송 조건과 문자열 ([02-중복-코드](02-중복-코드.md) 참조)

**개선 대상** (권장 순서)

| 순서 | 대상 | 기법 | 기대 효과 |
|:-:|---|---|---|
| 1 | `processApproval` | **메서드 추출** - action별 `submit` / `approve` / `reject` / `cancel` private 메서드로 분리, 본체는 분기 위임만 | 86줄 → 본체 약 15줄, 분기당 20줄 이하 |
| 2 | 추출된 각 메서드 | **조기 반환(Guard Clause)** - 상태·본인·권한 불만족이면 바로 return | 중첩 5 → 1~2 |
| 3 | 상태·권한·본인 판정 | **도메인 이동(Rich Domain)** - `approval.isSubmittable()`, `user.hasApprovalAuthority()` 등 | 서비스에서 규칙 계산 제거 |
| 4 | `NoticeService.publish` | 조기 반환 + 긴급 메일 발송부 메서드 추출 | 중첩 4 → 2 |
| 5 | `ScheduleService.create` | 입력 검증·겹침 검사 메서드 추출 | 39줄 → 20줄 안팎, `flag1` 제거 |
| 6 | `ApprovalService.create` | (길이 문제 아님) 긴 파라미터 목록 → 요청 DTO(record) - 단 public 시그니처 유지 조건 하에서 검토 | |

> `processApproval`은 순환 복잡도 약 25, 테스트 0개 상태다. **분기별 특성화 테스트(정상 전이 + 조용히 무시되는 경우)를 먼저 작성**해 현재 동작을 고정한 뒤에 쪼갠다.
