# 07. 스멜 심각도 점수 - 영향도 × 수정난이도

> **이 문서는 무엇을·왜 보는가**
> 스멜의 무게는 "얼마나 해로운가(영향도)"만으로 정해지지 않는다. 같은 해로움이라도 **고치기 어려울수록 오래 남고, 고치다 동작을 깨뜨릴 위험도 커진다.** 그래서 두 값을 곱해 심각도(★)를 매기면 "가장 무겁게 다뤄야 할 스멜"이 드러난다.
> 동시에 영향도와 난이도를 따로 보면 **해롭지만 쉽게 고칠 수 있는 것(Quick Win)** 도 함께 보여, 계획을 세울 때 "무엇이 가장 심각한가"와 "무엇부터 손댈까"를 구분해 판단할 수 있다.

- 기준 시점: 커밋 `7117ff4` (main)
- 대상: [docs/smells.md](../smells.md) 의 S01~S20
- 함께 보기: [06-심각도-표](06-심각도-표.md)는 영향·범위·선행성의 **합**으로 작업 순서를 정했다. 이 문서는 영향도 × 난이도의 **곱**으로 스멜 자체의 무게를 잰다

## 채점 기준

**영향도** - 그대로 두면 무엇이 어려운가

| 점수 | 기준 |
|:-:|---|
| 5 | 이것 때문에 다른 변경이 안전하지 않다 (버그 유입·동작 보존 증명 불가) |
| 4 | 업무 규칙이 흩어지거나 숨어 있어 변경 시 놓치기 쉽다 |
| 3 | 같은 수정을 여러 곳에 해야 하거나 테스트가 어렵다 |
| 2 | 읽고 이해하는 데 시간이 더 든다 |
| 1 | 보기 불편한 수준 |

**수정난이도** - 이 프로젝트의 불변 규칙(API·public 시그니처·DB값·조용히 무시하는 동작 보존)을 지키며 고치는 비용

| 점수 | 기준 |
|:-:|---|
| 5 | 여러 스멜을 먼저 풀어야 손댈 수 있고, 클래스 구조가 바뀐다 |
| 4 | 보존할 분기·값이 많아 놓치면 동작이 바뀐다 (위험 큼) |
| 3 | 손볼 곳이 여러 파일이고 출력 형식까지 맞춰야 한다 |
| 2 | 기계적인 추출·주입으로 끝나며 동작 변화 위험이 작다 |
| 1 | 이름 바꾸기·삭제 수준, IDE 기능으로 끝난다 |

**심각도 = 영향도 × 수정난이도** (1~25)

| 점수 | 1~4 | 5~9 | 10~14 | 15~19 | 20~25 |
|---|:-:|:-:|:-:|:-:|:-:|
| 심각도 | ★ | ★★ | ★★★ | ★★★★ | ★★★★★ |

## 영향도 × 난이도 사분면 - 무엇부터 손댈까

```
 영향도
   5 │                           S01         S03   S02
   4 │          S06 S08                S04 S09 (S19)
   3 │          S05 S07 S10  S12
     │   (S20)
   2 │   S11 S14 S17   S13
     │   S15 S18
   1 │   S16
     └──────────────────────────────────────────────── 난이도
         1      2      3      4      5
```

나누는 기준: 영향도 **3 이상 = 높음**, 난이도 **3 이상 = 어려움**. (범위 밖 S19·S20 제외)

| 사분면 | 해당 스멜 | 전략 |
|---|---|---|
| **영향 높음 · 쉬움 (Quick Win)** | S06, S08, S05, S07, S10 | 위험이 작고 효과가 크다. **특성화 테스트 직후 가장 먼저** |
| **영향 높음 · 어려움 (핵심 과제)** | S01, S03, S04, S09, S02, S12 | 심각도 최상위. 테스트(S01)로 안전망을 깔고 S04 → S03 → S09 → S02 순으로 단계적으로. S12는 JSON 형식 보존 부담이 커서 이들 뒤에 |
| **영향 낮음 · 쉬움 (곁들이기)** | S11, S14, S15, S16, S17, S18 | 따로 일정을 잡지 않고 관련 리팩토링 때 함께 |
| **영향 낮음 · 어려움 (보류)** | S13 | public 시그니처를 유지해야 해서 우회 비용이 크다. 핵심 과제가 끝난 뒤 |

## 정리

- **가장 심각한 스멜은 S02(거대 클래스)와 S03(긴 메서드)** - 둘 다 `ApprovalService` 에 있고, 다른 스멜이 풀려야 고칠 수 있는 "결과로서의 스멜"이다.
- 그래서 **심각도 순서 ≠ 작업 순서**다. 작업은 [06-심각도-표](06-심각도-표.md)의 단계대로 S01(테스트) → Quick Win(S06·S05·S07·S08) → S04 → S03 → S09 → S02 로 진행하는 것이 안전하다.
- **보존 대상**: 어떤 스멜을 고치든 API·public 시그니처·DB 정수값·조용히 무시하는 동작·메일/로그 출력 문자열은 그대로 둔다. S19는 동작 변경이므로 리팩토링이 끝난 뒤 재설계 단계에서 다룬다.
