# refactor - 레거시 리팩토링 10단계

레거시 코드를 **겉보기 동작은 100% 그대로 두고 내부 구조만** 단계적으로 개선한다.
「클린코드 & 리팩토링 실전」 legacy-portal(결재 · 공지 · 일정) 실습에서 이틀 동안 실제로 밟은 순서다.

리팩토링이 무서운 이유는 "고쳤는데 뭔가 달라졌는지 모른다"이기 때문이다. 이 스킬의 모든 규칙은
그 불안을 없애는 쪽으로 짜여 있다 - 먼저 현재 동작을 테스트로 박제하고, 작게 바꾸고, 바로 확인하고, 한 단계씩 커밋한다.

## 0. 시작 전에 확인할 것

1. 프로젝트 `CLAUDE.md` 를 읽는다. 리팩토링 규칙(불변 규칙 · 네이밍 · 주석 규칙)이 있으면 그것이 이 스킬보다 우선한다.
2. 빌드 · 테스트 명령을 찾는다 (`./mvnw test`, Windows 는 `.\mvnw.cmd test`). JDK 버전이 맞는지 한 번 돌려 본다.
3. 사용자가 **어느 단계부터** 원하는지 확인한다. 처음이면 1단계부터. 중간 단계를 요청하면 그 단계의 전제(특히 2단계 특성화 테스트)가 있는지 먼저 본다 - 없으면 안전망부터 만들자고 제안한다.
4. 커밋 · push 는 사용자가 원할 때만 한다. 이 스킬의 "한 단계 한 커밋"은 **커밋 단위를 그렇게 나눈다**는 뜻이지, 묻지 않고 커밋하라는 뜻이 아니다. 사용자가 단계마다 커밋을 맡겼으면 그대로 진행한다.

## 1. 철칙 - 외부에서 관찰 가능한 것은 바꾸지 않는다

| 보존 대상 | 구체적으로 |
|---|---|
| API | URL · HTTP 메서드 · 요청/응답 JSON 필드 이름 · 순서 · 타입(정수 code 그대로) · 상태 코드 |
| DB 저장값 | enum 을 도입해도 DB 에는 기존 정수(0/1/2/3/9…) - `@Convert` + `AttributeConverter`. `@Enumerated(STRING/ORDINAL)` 금지 (ORDINAL 은 9 같은 비연속 값에서 어긋난다) |
| public 시그니처 | 메서드 이름 · 인자 · 반환 타입. 새 진입점을 **추가**하고 옛 것은 **위임**만 하게 둔다 |
| 동작 | "조용히 무시"(return) · null 반환 · 예외 종류 · 저장 → 메일 → 로그 순서 · 출력 문자열 1글자까지 |

**레거시의 결함도 이 단계에서는 보존한다.** 권한 없는 승인을 조용히 무시하는 것이 나빠 보여도, 그걸 예외로 바꾸면 리팩토링이 아니라 동작 변경이다. 결함은 테스트 이름 · 주석에 `[보존 대상 · 결함 후보]` 로 표시해 두고, 리팩토링이 끝난 뒤 **재설계 단계**에서 다룬다.

### 특성화 테스트는 안전망 - 본문을 고치지 않는다

한번 만든 특성화 테스트의 **호출 · 기대값은 수정하지 않는다.** 테스트가 바뀌면 "동작이 그대로다"를 증명할 수 없기 때문이다.
- 허용되는 것: 클래스 이름 · 패키지 변경에 따른 import · `@Import` 줄 같은 기계적 수정. 바꿨다면 diff 를 보여 주고 호출 · 기대값이 그대로임을 확인받는다.
- enum 을 도입해도 테스트는 정수 리터럴(0/1/2/3/9)로 검증한다. enum 상수 비교로 바꾸지 않는다.
- "사용처 전부 수정"이라는 지시가 있어도 테스트는 사용처가 아니라 안전망이다 - 제외한다.

## 2. 모든 단계에 공통인 작업 루프

```
① 범위 확인  : 이 단계에서 바꿀 파일 · 바꾸지 않을 것(보존 대상)을 짧게 말한다
② 변경       : 작게 바꾼다. 한 번에 한 가지 기법
③ diff 검토  : 사용자가 "diff 검토 후 적용"을 원하면 적용 전에 diff 요약을 보여 주고 기다린다
④ 테스트     : ./mvnw test (가능하면 clean test). 실패하면 테스트가 아니라 코드를 고친다
⑤ 추가 확인  : 테스트가 덮지 않는 동작(필드 생략 시 500, 콘솔 출력 등)은 임시 테스트로 확인하고 지운다
⑥ 커밋       : 한 단계 = 한 커밋 (예: "refactor: ... (R08)"). 테스트 추가는 test:, 문서는 docs: 로 따로
⑦ 보고       : 무엇을 · 어떤 기법으로 · 왜 바꿨는지, 보존한 것, 테스트 개수와 결과, 남은 것
```

- 테스트가 실패했을 때 기대값을 고쳐 green 을 만들지 않는다. 그건 안전망을 끊는 일이다. 단 **특성화 테스트를 새로 쓰는 중**이라면 기대값은 "현재 코드의 실제 결과"이므로, 관찰 결과에 맞추는 것이 맞다.
- 리팩토링한 코드에는 학습용 주석을 남긴다 - 클래스 상단 `[리팩토링] 레거시 X → Y (기법 · 이유)`, 변경 지점 인라인 `[보존] ...`. 코드만 봐도 "무엇을 · 어떤 기법으로 · 왜" 고쳤는지 보이게.
- 이름은 약어 금지(`d` → `approval`, `u` → `user`, `flag1` → `isOverlapping`), boolean 은 `is/has`, 테스트 메서드명만 한글 시나리오 허용.

## 3. 10단계

각 단계의 상세 절차 · Before/After 예시 · 함정은 `references/steps.md` 에 있다. **해당 단계를 시작할 때 그 절만 읽는다.**

| # | 단계 | 핵심 기법 | 완료 기준 | 커밋 예 |
|---|---|---|---|---|
| 1 | **진단** | 구조 파악 · 스멜 목록(심각도 ★) · 리팩토링 백로그(R01~) · (선택) SonarQube 기준선 | `docs/진단/*.md`, `docs/smells.md` - 코드 변경 없음 | `docs: 진단 - 스멜 목록과 백로그` |
| 2 | **특성화 테스트** | 현재 동작을 그대로 박제 (`@DataJpaTest` · MockMvc · 출력 캡처 · JDBC 로 DB 값) · JaCoCo 로 빈 분기 찾아 보강 | 리팩토링 대상의 실행 가능한 분기 100% 근접, 전부 green | `test: X 특성화 테스트 N개 (안전망)` |
| 3 | **매직넘버 · 식별자** | 숫자 → enum(+Converter, DB 정수 보존) · 이름 바꾸기 | 서비스 안 숫자 비교 0, 약어 0 | `refactor: status int → XStatus enum (R06)` |
| 4 | **메서드 추출 · 가드 절** | Extract Method · 중첩 if → 조기 return(가드 절) | 긴 메서드 분해, 중첩 3단 이상 0 | `refactor: processApproval 을 submit/approve/... 로 추출 (R08)` |
| 5 | **계층 · DTO** | `Map` 요청 · Entity 응답 → 요청/응답 DTO(record), 긴 매개변수 → 명령 객체 | JSON 형식 그대로, 컨트롤러가 DTO 를 풀어 넘기지 않음 | `refactor: 요청/응답 DTO 분리 (R11)` |
| 6 | **책임 분리 (SRP)** | 변경 이유별로 클래스 추출 (알림 · 감사 · 코드 해석 · 생성 규칙) | 서비스에 흐름 조율만 남음 | `refactor: XService 책임 분리 (R10)` |
| 7 | **DIP** | 직접 `new` → 인터페이스 추출 + 생성자 주입, 구현체 이름 정직하게 | 서비스 안 협력 객체 `new` 0, 테스트에 Fake/Mock 주입 가능 | `refactor: MailSender 인터페이스 + 주입 (R02 · R03)` |
| 8 | **중복 제거** | 동일 · 유사 · 우연 중복 구분 → 동일 · 유사만 한 곳으로 | 포맷 · 줄 조립 복붙 1곳 | `refactor: 감사로그 형식을 한 곳으로` |
| 9 | **도메인** | Tell, Don't Ask · 상태 전이 · 권한 판정을 엔티티로 · 정적 팩토리 · 엔티티 메서드는 `boolean` 반환 | 서비스가 getter 로 꺼내 비교하는 규칙 0 | `refactor: 상태 전이를 X 엔티티로 (R09)` |
| 10 | **보고서** | 전/후 같은 도구로 측정 → `REPORT.md` (지표 표 · ↑/↓ 방향 · Before/After 스니펫) | 숫자는 전부 실측, 표 열 개수 검증 | `docs: 리팩토링 전/후 비교 보고서` |

순서에는 이유가 있다. 2단계(안전망)가 없으면 3단계 이후 어떤 변경도 증명할 수 없다. 3 · 4단계로 코드를 읽기 쉽게 만든 다음에야 5 ~ 9단계의 구조 변경이 안전하다. 사용자가 순서를 바꾸자고 하면 따르되, 안전망이 없는 상태라면 그 위험을 한 줄로 알린다.

## 4. 자주 빠지는 함정 (실습에서 실제로 겪은 것)

- **우연 중복을 합치지 않는다.** `role >= 2` 가 결재 권한 · 공지 게시 권한에 똑같이 있어도 다른 규칙이다. 합치면 한쪽 정책 변경이 다른 쪽까지 바꾼다 → `hasApprovalAuthority()` · `hasNoticePublishAuthority()` 로 따로 둔다. 상태 코드 9 가 "취소"와 "내림"으로 뜻이 다르면 공통 상수로 묶지 않는다.
- **엔티티에 새 메서드를 넣을 때 JSON 필드가 늘지 않게** - 응답에 엔티티가 그대로 나가는 동안은 `get`/`is` 접두를 피한다(`approvalStatus()`, `hasX()`, 인자 있는 메서드).
- **DTO 의 null 처리 차이** - `Map` 은 "키 없음"과 "값 null"을 구분하지만 record 는 못 한다. 필드 생략 시 레거시가 500(NPE)이었다면 언박싱 · `.longValue()` 위치와 순서를 맞춰 그대로 재현하고, 임시 MockMvc 테스트로 확인한다. 정상 요청에 영향 없는 차이는 "알려진 차이"로 문서화한다.
- **`@DataJpaTest` 에서 JDBC 로 컬럼을 읽기 전엔 `entityManager.flush()`** - 안 하면 변경이 아직 DB 에 없어 값이 다르게 읽힌다.
- **겹침 검사 같은 루프를 `anyMatch` 로 바꾸면 short-circuit 으로 동작이 달라질 수 있다** (중간 예외가 사라짐). 레거시가 끝까지 돌았다면 끝까지 돌게 둔다.
- **null 결함도 보존** - `owner.equals(...)` 로 NPE 가 나던 코드를 엔티티로 옮길 때 null 가드를 넣으면 동작 변경이다. 검사 순서까지 유지한다.
- **커밋에 섞지 말 것** - 로컬 설정(`settings.local.json`), 작업 관리 파일(TODO.md 등)은 `git add -A` 대신 파일을 지정해 뺀다.
- **문서를 스크립트로 고칠 때** 표 구분선 `|---|` 을 문단 구분선 `---` 으로 오인하기 쉽다. 고친 뒤 표마다 `|` 개수가 같은지 검사한다.

## 5. 측정 도구 (10단계 · 진행 중 점검)

- `scripts/method-metrics.cjs <src/main/java>` - 메서드별 줄 수 · 중첩 깊이 (긴 순). 레거시는 `git archive <커밋> src/main | tar -x -C <임시폴더>` 로 풀어 같은 스크립트로 잰다.
- `scripts/coverage-summary.sh <jacoco.csv>` - 클래스별 줄 · 분기 커버리지와 합계 (`./mvnw test` 후 `target/site/jacoco/jacoco.csv`, pom 에 jacoco-maven-plugin 필요).
- 놓친 분기 위치: `target/site/jacoco/<패키지>/<클래스>.java.html` 에서 `title="1 of 2 branches missed."` 를 찾는다. enum `switch` 의 숨은 default 처럼 실행될 수 없는 분기는 보고서에 이유를 적는다.

보고서 양식은 `references/report-template.md` 에 있다.

## 6. 단계 보고 형식

단계가 끝날 때마다 짧게:

```
## N단계 <이름> 완료
- 바꾼 것: 파일 · 기법 · 이유 (표 1개)
- 보존 확인: 무엇을 어떻게 확인했나 (테스트 N개 green, 임시 확인 등)
- 테스트: ./mvnw test → Tests run: N, Failures: 0
- 커밋: <해시> <메시지>   (커밋 안 했으면 "커밋 대기")
- 남은 것 / 다음 단계
```
